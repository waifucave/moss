# The secrets file on Windows and Linux (spec §9.1, §8.5; spike S8)

On macOS MOSS keeps its secrets in the Keychain, items that trust the daemon's binary alone. Windows' Credential Manager and the Linux Secret Service have no such per-program check, so there MOSS keeps its secrets in **one encrypted file in its home, `secrets.enc`, and the file's key in the OS store**. What a tool or plugin that is not the daemon can reach is then decided by the fence (spec §9.1), not by the OS store.

## How it is built

| Part | File | What it does |
|---|---|---|
| Names | `packages/core/src/secrets/secret-files.ts` | The ONE spelling of `secrets.enc`, `secrets.key`, `secrets.key.cred` and the lock. The fence's layout, the bots' read-deny list (`BOT_READ_DENIED`), the home's named denials, the old-home copy and the other-installs check read it. A file added to the list is hidden everywhere at once. |
| The file | `packages/core/src/secrets/moss-secret-store.ts` (`EncryptedFileValues`) | AES-256-GCM, a fresh 96-bit nonce per write, the format byte and the key's source as authenticated data, one 32-byte random key. A write reads the file whole, changes it and writes it whole, under the lock. |
| Where the key is | same file, `chooseFileStore` | A file already made keeps its key's source and answers `locked` while it can't be reached; a new one takes Credential Manager (Windows), an unlocked Secret Service (Linux), a locked one that someone can unlock (waited for), `systemd-creds --user`, and last a key file only the user can read, labelled `plaintext` (`secretStoreWarning`). A key is made only while there is no file: a missing key never becomes a new, empty store. |
| The disk | `packages/core/src/secrets/private-file.ts` | `writePrivateFile`: empty under a temporary name **in the run folder** (never beside the file under a name no deny list knows), locked down (0600; on Windows `icacls /inheritance:r /grant:r *<user SID>:F`), written, **the file flushed** (`fsync`; `FlushFileBuffers` on Windows), renamed over the old file, and **the rename made durable**. It returns only then. See "Durability" below. `withSecretsLock`: one writer at a time in a process and across this user's processes (`<home>/run/secrets-file.lock`, pid and time, taken over when the pid is gone or the lock is far older than any write). |
| The flat-name store | `packages/core/src/secrets/file-backend.ts`, `auth/secret-store.ts` | `defaultSecretsBackend()` on Windows and Linux is the file (`kc/<service>/<name>` items); on macOS it is the Keychain as before. `KeychainSecretStore`, the CLI's token reads and the MCP sign-in store (`runtime-sdk/mcp-oauth-store.ts`) all go through it. The raw OS store (`osSecretsBackend`) holds only the file's key and is what the one-time move reads. |
| The one-time move | `moveOsStoreItems` | On the first open: every known name is read from the OS store; in ONE hold of the file's lock the file is read again and every item it does not hold yet is added (a value the file already has is the newer one and is kept), and the file is written durably; only after that returns is an original deleted from the OS store (and only when the file's value is the same); the note that the move is done is written last. With the OS store silent (a locked keyring with no display), nothing is written, the next start tries again, and meanwhile a `get` of a name that may still be there and is not in the file throws `locked` (see "While the move is unfinished"). `Bun.secrets` cannot list on Windows or Linux, so the names are the known ones (`MIGRATION_B_SECRET_NAMES` and the catalog's provider slots); sign-ins whose names are made from an id at run time (`mcp-oauth:<id>`) are not moved and are made again. |
| The contract store | `MossSecretStore` | The device key, link keys, plugin secrets, routine webhook keys and the registry's keys: the same file, items `core/…`, `plugin:<id>/…`, `device/…`, plus an index in `credentials/index.json` (names and times, never a value). See "The index" below. |

The one-reader rule is a test: `packages/core/test/secrets/one-reader.test.ts` lists the only files that name `Bun.secrets` as a value and the only file that builds an SDK keychain store.

## What each secret is, where it lives, and who may read it

"The daemon" is `moss-core` (and the CLI, the same binary, run by the user). "Fenced" means a command a model runs (Bash or PowerShell, a coding agent's command, a plugin's hook): the fence hides the file and its key files from it (Linux: not mounted in a tmpfs view of the home; macOS: Seatbelt deny; Windows: DACL deny for the sandbox principal, lane WS). Plugin code and the user's own programs run as the user and can read what the user can read (spec §5: plugin code is trusted once the user says OK).

| Secret | macOS | Windows | Linux | Who may read |
|---|---|---|---|---|
| Provider API keys (`<provider>:default`), Codex and Console sign-ins (`codex-oauth:default`, `anthropic:console`), tool keys (`exa-api-key`) | Keychain item (daemon's ACL) | `secrets.enc` | `secrets.enc` | The daemon; children get a value only by `credential_resolve` for a ref their options named. Not fenced commands. |
| Pairing tokens (`harness-token`, `admin-token`, `remote-token`) | Keychain item (daemon and the app) | `secrets.enc` | `secrets.enc` | The daemon and the CLI. The desktop apps do not read them. Not fenced commands. |
| MCP sign-ins and client records (`mcp-oauth:<id>`, `mcp-oauth-client*`) | Keychain item | `secrets.enc` | `secrets.enc` | The daemon. |
| Device key, link keys, registry keys, routine webhook keys, plugins' own secrets | Keychain items (`<service>.items`) | `secrets.enc` (contract store) | `secrets.enc` (contract store) | The daemon; a plugin only its own, through the core (`secrets.get`). |

## Durability (what a power cut can and cannot do)

A secret counts as saved only when `writePrivateFile` returns. Its steps, in order (the tests in `test/secrets/secrets-file-durable.test.ts` record the calls and inject a crash between each pair):

1. the half-made copy is created in `<home>/run/`, locked to the user, written;
2. the file is flushed to the disk (`fsyncSync`: `fsync` on Linux and macOS, `FlushFileBuffers` on Windows);
3. it is renamed over the real name and the rename is flushed. Linux and macOS: `fsync` of the folder after it (both folders when the copy was made in another), which is what makes a rename survive a power cut. Windows: a folder cannot be flushed, so the renamed file is flushed again (`FlushFileBuffers` on a handle opened on it). **What that guarantees, exactly:** the file's data is on the disk before the rename (step 2), so a power cut leaves the old whole file or the new whole file, never a short one. That the rename itself survives is NOT promised by Microsoft in so many words: it relies on NTFS committing a file's pending metadata, its directory entry included, through its log when the file is flushed. `MOVEFILE_WRITE_THROUGH` is not used: it is documented only for a move made as a copy and a delete, not for a same-volume rename. A power-cut test on real Windows hardware is therefore an owner-only check (see below);
4. a store write first writes its NEW content as the second copy `credentials/secrets.enc.bak` (itself written this way), then writes the file, then, once, the note `credentials/secrets-file.made` (lane SE: the copy used to be the file it replaced, which brought removed items and replaced values back when the file was later damaged).

So at every instant the name holds the old whole file or the new whole file, and the second copy beside it is the newest whole file a write began; it never holds what a write that returned replaced or removed. On Windows the very first write of a new file has no previous copy: there the one-time move depends on the flush of the renamed file above before it deletes anything from Credential Manager. What this does not promise: a disk that lies about its flush, and macOS's `fsync` (which does not flush the drive's own cache; macOS does not use this file).

**A file that is short, empty or changed** (a bad disk, another program) is read from the previous copy, and a line says so; the next write puts a whole file back. With no previous copy it is an error (`invalid` or `locked`), never an empty store, and nothing is written over it. **A file deleted while its key is still kept** is read from the previous copy if that is there; with neither, and the note that a file was made here still there, it is `locked` and says so: the person restores it, or deletes `credentials/secrets-file.made` to start empty. A key made and a crash before the first file leaves no note, so that is the first start again, not a lost file. The note is a file: deleting `secrets.enc`, its previous copy AND the whole `credentials/` folder together leaves the key in the OS store with nothing saying a file was ever made, and the store opens empty (as it would after the home itself is deleted). Keeping the note beside the key in the OS store would close that; it is not built.

Not done (backlog): rollback protection (an older whole file put back by someone who can write the home: a generation or the home's id in the authenticated data).

## The index (every OS, macOS included)

The contract store keeps each item's owner, name, generation and time in `credentials/index.json`. **The values are the authority, not the index**: `get` answers what the value backend (the file, or the Keychain on macOS) holds, so an index that is damaged, short, missing or behind (a crash after a value was written and before its entry) never makes a stored item read as absent, and nothing that makes an item when it finds none (the device key, `DeviceKey.loadOrCreate`) makes one over the old. An item the index doesn't know reads with generation 0. Before lane SE (2026-11-24) a damaged index read as an empty store, and the next start made a new device key.

The index is written as the secrets file is (`writePrivateFile`), then a second whole copy, `credentials/index.json.bak`, then once the note `credentials/index.made`. A damaged or missing index is read from the second copy, and a line says so once. With neither copy readable, a write, a removal and a listing are refused (`invalid` when the index is there but damaged, `locked` when both are gone though the note says one was made), and nothing is written over them: the person restores one, or deletes them with the note to start the list afresh (the values stay and still read). A write of an item and its entry holds `run/secrets-index.lock` across this user's processes, taken before the file's own lock, so the daemon and the CLI writing at once lose no entry. Tests: `test/secrets/secret-index.test.ts`.

## Rules added by lane SE's review round (2026-11-24)

* **A removed secret, or a replaced value, never comes back.** Every write makes the second copy (`credentials/secrets.enc.bak`) the NEW file first, then replaces the file (round 2 widened this from removals to every write: a rotated webhook key or refreshed token came back from the copy too, and an item just added was lost to damage of the file, which would make a device key be minted again). A crash between the two leaves the old file (the removal never returned, so it never happened) beside a copy that already lacks the item; after it, neither copy holds it, so damage or a restore of either copy later never brings it back, and a later write never folds it back in. Tests: `test/secrets/review-round.test.ts` (every crash step, every harm to either copy, generated sequences).
* **"Can't look now" is never "not there".** Every check for the file, its previous copy, its note, the key files and the index (`present` in `private-file.ts`) takes only "no such file" as absent; any other failure (EACCES, EIO, a share gone) is `locked` with the error's code in the reason, so nothing is minted over a file that is merely unreadable. The daemon still starts (the store opens locked).
* **A holder taken over never writes.** Every write made under a lock (the file, its copy, the index, a key file) checks right before its rename that each lock the work holds still carries this holder's text (`assertLocksHeld`, an AsyncLocalStorage of the held locks); one paused past the limit (a lid closed during a keyring prompt, a suspended VM) and taken over meanwhile drops its write with `locked`. Renewal writes the lock whole under another name and renames it into place.
* **The lock.** A lock dated more than 5 s in the future is stale. A holder renews its lock every 20 s while it holds it (a keyring prompt can take minutes), and removes only a lock whose text is still its own. Who can write `run/`, and so plant a lock: the user's own processes, and on Windows and Linux a plugin's host half (it runs as the user, spec §5.2); not bots' or agents' commands (the fence write-denies `run/`), not the Windows pool accounts (a deny ACE), not a macOS plugin host (its sandbox). A planted lock holds writes for at most 120 s unless its planter keeps renewing it, which only a process of the user can.
* **Made once, even from two processes.** Everything that makes an item when it finds none reads, or makes and writes, in one step under the lock: `getOrCreateSecret` (contracts/secret-store.ts, `MossSecretStore.getOrCreate` under the index's lock) for the device key, the box key, a plugin's sealing keys (`keys.publicKey`, whose scoped store passes `getOrCreate` through), a routine's webhook key and the registry's key; `getOrSet` on the file backend (one hold of the file's lock) for the pairing tokens (`TokenAuthority`). The macOS Keychain has no such step: there the tokens are read, then written, as before.
* **A home from before this lane** has an index but no `credentials/index.made`: the note is written the first time its index reads whole, so losing both copies after that is `locked`. Lost before the first read under this build, the list starts EMPTY: every value still reads by name (the device key and the logins work), but `list` shows nothing until items are written again, so a plugin's secrets and synced items are not listed for removal or sync. The note is written without the lock and without waiting (a constant text, written whole and renamed; two writers write the same bytes).

## While the move is unfinished

If the OS store did not answer the move (a locked keyring with no display to ask on), the flat store refuses to answer "nothing" for a known name that is not in the file yet: it throws `locked`, because the callers make a NEW pairing token for a missing one and the next start would keep the new tokens and strand the old, unpairing every device with no message. One plain line goes to the daemon log, once: the keyring holds the saved logins from the previous version, MOSS makes no new tokens or logins in their place, unlock it and start again. The move is tried again at the next call after 30 seconds, not on every call. Where there is no Secret Service at all (a headless computer, the probe failing as D-Bus does with no bus) nothing was ever there to move, and nothing waits.

## What the fence does about it

* **Hidden from Bash and the agents.** `fence/layout.ts` puts `secrets.enc` in the `secrets-file` kind and `secrets.key`, `secrets.key.cred` in `key-file`, both read-denied and write-denied, with the run folder (`run-folder`) and `credentials/`. The previous copy and the note are in `credentials/`, and the half-made copies in `run/`, so no file of the store sits under a name a deny list does not know. The tree served to a bot or a peer refuses all of them (`contracts/conformance/tree.ts`); the old-home copy leaves `credentials/`, `run/` and the three names out; I found no sync or export that names the home's files (sessions sync by their own records). On Linux (`fence/linux-bwrap.ts`) the MOSS home is a tmpfs view that holds only the runner's own folders, so a name denied here is absent, not refused: a file made after the command started does not appear either. `test/fence/secrets-file-fence.test.ts` runs real bubblewrap on the CI runner and tries `cat`, `cp`, a planted soft link and hard link, `/proc/self/root`, `find`, a write, an `mv` of the home, and a file made mid-run, for a coding agent's command and a bot's.
* **Windows, for real.** `test/fence/win-fenced.e2e.test.ts` (the windows-fence workflow) has a pool principal's Bash and PowerShell try to read the files the real store wrote (`secrets.enc`, its previous copy, the index and its copy) and list Credential Manager, where the user's own process reads each file and lists the key (the control).
* **Another account.** `test/secrets/other-account.test.ts` makes a throwaway user on the Linux runner (`sudo -n useradd`) and has it read every file the store wrote, before and after every folder is opened to everyone, with a plain file beside them read as the control.
* **The agents' own sandboxes.** The deny list `BOT_READ_DENIED` (which carries the three names) is what the agent settings writers (`fence/sandbox-settings.ts`) and the runtime's home deny (`runtime-sdk/turn-loop/home-deny.ts`) are built from. Each agent is admitted only per exact backend, version and configuration (spec §9.3, §14.1 item 8); none is admitted yet, and an agent with no sandbox on Windows or Linux starts only after the user's OK.
* **`systemd-run --user` and the Secret Service are closed on Linux by hiding, not filtering.** The sandbox has no network namespace access, `socket(AF_UNIX)` fails (`fence/seccomp.ts`), `/run/user/<uid>` is an empty tmpfs and the system bus socket is nulled, so a command cannot reach the session bus, systemd's sockets, the Secret Service or portals at all.

## For lane WS (the Windows sandbox)

* The names to deny are `SECRET_FILE_NAMES` (`secrets/secret-files.ts`), already in the fenced set's `secrets-file` and `key-file` kinds and in `BOT_READ_DENIED`. `fence/win-sandbox.ts` builds its `--deny-read` list from `policy.denyRead` and `BOT_READ_DENIED`, so it picks them up with no change; **read-deny on Windows means a DACL deny ACE for the sandbox principal on `secrets.enc`, `secrets.key`, `secrets.key.cred`, `run\` and `credentials\`** (a deny wins over any grant the principal gets on the home).
* The file is already locked to the user's SID alone with inheritance off (`lockToOwner`), so the principal has no access to it even where its grants cover the home; the deny ACE is the second line.
* The key is in the user's Credential Manager (DPAPI, per user): the sandbox principal is another account and cannot read it.

## Linux: the Secret Service broker (specified, not built)

The spec (§4, §9.1; S8) wants `gh`, Docker and git to keep the OS store from inside a fenced Bash while MOSS's own items stay out of reach. The closure above (nothing reaches the bus) is the safe half; the broker is what would give those tools their own logins back. It is a lane of its own: it needs a Secret Service (D-Bus) server in the daemon, a socket the sandbox is allowed to open, and a policy; none of that exists, and the sandbox's seccomp filter forbids the `socket(AF_UNIX)` it would need. Specification:

1. **Where it runs.** In the daemon, as a D-Bus peer on a private bus it owns (not the user's session bus), speaking `org.freedesktop.secrets` to a fenced command only through one Unix socket bound into the sandbox (`--bind <home>/run/broker/<session>.sock`). The sandbox's seccomp filter then allows `connect` to that one path only: either by a second filter that allows `AF_UNIX` and a bind-mount that leaves only that socket in the sandbox's tree (the tmpfs view already hides every other socket path), or by passing the connected socket as an inherited file descriptor with `AF_UNIX` still closed.
2. **What it serves.** Items of its own, never the user's keyring wholesale: a table of the logins the user allowed for that session, destination and identity (git hosts, `gh`'s `github.com`, Docker registries), each a collection item with attributes. `SearchItems`, `GetSecret(s)`, `Unlock`, `OpenSession` and `ReadAlias` are answered from the table; every method that creates, writes, deletes or changes a collection is refused.
3. **Authorization by what a request and its answer carry**, not by bus name, interface or object path. S8's finding: an xdg-dbus-proxy path allow list forwarded a protected item's path in `GetSecrets`'s arguments. The broker validates every item path in every request body (`GetSecrets`, `SearchItems` results, `Unlock`'s list) against the table and every returned item against the session's grant, binds each D-Bus session to its caller, and denies unknown methods.
4. **Never served:** the contents of `secrets.enc`, the file's key item, approval tokens, device keys, or any item not in the table. The broker holds only what the core hands it for that session.
5. **Acceptance:** the spike's `spikes/s8-secrets/secret-broker.py` harness (`proxy-probe.py --bwrap`, 13 of 13 assertions: hidden search and listing, direct and mixed bulk denial, three host-broker destinations denied, `gh`, Docker and git lookups served, a real `git credential fill`, a fenced lookup of MOSS's own item denied) rewritten against the daemon's broker on the Linux runner, plus S8's three open points: write, login and unlock flows, reconnect and concurrency, and the sandbox's hidden execution endpoints (host bus, systemd sockets, portals, the Docker daemon socket).

On macOS the same need is met by the git credential helper that gets logins from the core (C1); on Windows by the credential broker running in the user's logon context (lane WS).

## What a runner cannot prove

* A real desktop keyring: GNOME Keyring or KWallet unlocked by the user's login, locked at the login screen, and a daemon that starts at login before the keyring is unlocked (today a locked keyring on an interactive Linux session makes the daemon's first token read throw `locked`, and the daemon does not start until it is unlocked).
* A reboot: the file and its key surviving one, on Windows (Credential Manager under the real logon), on Linux with the keyring, with `systemd-creds` (and a TPM), and with only the key file.
* `systemd-creds --user` with a real TPM, and on a computer with none (S8's own open gate).
* A power cut on real hardware: Windows (the renamed file's flush, above) and Linux (the folder's `fsync`), mid-write and mid-move.
* The Windows ACL on a normal non-administrator user's computer (the runner's user is an administrator, which is why SYSTEM and Administrators entries show on the file).
* Windows 11 as against the runner's Server image: the DPAPI and Credential Manager context a logon task or a sandbox principal gets (S8.1: a scheduled task as a password principal did not start in the spike).
